# Архитектура и технические решения

## Философия разработки

**KISS + Бритва Оккама + YAGNI** — простота, минимализм, никакой спекуляции

- **Минимум абстракций**: не создавай функции/типы "на будущее", только для реальной задачи
- **Явное > неявного**: код читается как инструкция, без скрытой магии
- **Одна ответственность**: функция делает одно, крейт решает одну задачу
- **Прямолинейность**: решение очевидно при чтении → правильно; требует расшифровки → переделай
- **Простота > элегантности**: работающий прямой код лучше "красивого" сложного

## Исходники zstd

Вендорятся в директорию `zstd/lib/` скриптом `zstd/update.ps1`.

Из полного архива zstd берём только нужное:
- `lib/zstd.h`, `lib/zstd_errors.h` — публичный API
- `lib/common/` — базовые примитивы
- `lib/compress/` — компрессия
- `lib/decompress/` — декомпрессия

Не нужно и удаляется после скачивания:
- `lib/legacy/` — поддержка форматов до v0.8
- `lib/dictBuilder/` — обучение словарей
- `lib/deprecated/` — устаревший API
- `lib/dll/` — Windows DLL сборка

Текущая версия хранится в `zstd/VERSION`.

### Многопоточность zstd

Флаг `-DZSTD_MULTITHREAD` **не используется** при сборке. Многопоточная компрессия/декомпрессия на уровне zstd не активирована. Файлы `zstdmt_compress.*` присутствуют в вендоре (они часть `compress/`), но без флага этот код неактивен.

Многопоточность в Zaster реализуется на уровне libzaster — мы сами распараллеливаем работу с tar-записями, а не делегируем это zstd.

## libzaster

Исходники в `lib/`, компилируется в статическую библиотеку `libzaster.a`.

Модули (в порядке зависимостей):
- `defs.h` — общие макросы (инлайнинг, видимость, предсказание ветвлений, типы)
- `memory.h`/`memory.c` — управление памятью (страничный аллокатор, сегменты)
- `tar.h`/`tar.c` — работа с tar-заголовками (UStar, GNU, PAX)
- `fs.h`/`fs.c` — файловые утилиты (пока заглушка)

## Сборка prebuilt

Компилятор: Clang (кросскомпиляция через Docker-образ `ghcr.io/powertech-center/alpine/cross-clang`).

Определения таргетов вынесены в общий файл `zstd/targets.ps1` (dot-sourcing).
Оба скрипта (`zstd/build.ps1` и `lib/build.ps1`) подключают его через `. "$PSScriptRoot/../zstd/targets.ps1"`.

Результат:
- `prebuilt/<таргет>/libzstd.a` — собранная из вендорных исходников, меняется редко
- `prebuilt/<таргет>/libzaster.a` — наша библиотека

## CLI

Исходники в `cli/`, собирается в бинарник `zaster`. Скрипт сборки: `cli/build.ps1`.

Собранные бинарники для всех таргетов — в `dist/`.

## Макросы инлайнинга

- `ZASTER_INLINE` → `static inline` + атрибут. Для свободных функций в C-заголовках. `static` нужен, чтобы избежать конфликтов линковки при включении из нескольких `.c` файлов.
- `ZASTER_ALWAYS_INLINE` → `inline` + атрибут (без `static`). Для методов C++ классов, где `static` меняет семантику (делает метод статическим, убирает `this`).

## Скрипты инфраструктуры

Пишутся на PowerShell (`.ps1`) — работает на Windows, Linux и macOS.
Все комментарии и строки в скриптах — на английском языке.
