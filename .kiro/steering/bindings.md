# Биндинги и публичный API

## Общий принцип

Zaster — библиотека на Си с prebuilt-статическими библиотеками. Каждый биндинг — это тонкая обёртка, которая:
1. Линкует `libzaster.a` и `libzstd.a` из `prebuilt/<target>/`
2. Предоставляет идиоматичный API для своего языка
3. Имеет fallback на сборку из исходников для экзотических платформ

## C

Заголовок-агрегатор `zaster.h` в корне. Включает в порядке зависимостей:
1. `zstd/lib/zstd.h`, `zstd/lib/zstd_errors.h`
2. `lib/defs.h`
3. `lib/memory.h`, `lib/tar.h`, `lib/fs.h`

## C++

Заголовок `zaster.hpp` в корне. Обёртки над C API:
- `namespace zstd::` — функции и типы zstd
- `namespace zaster::` — функции и типы libzaster (вложенные: `memory::`, `tar::`, `fs::`)

Правила маппинга C → C++ описаны в `porting.md`.

## Системы сборки C/C++

Четыре альтернативных способа подключения для потребителей:

| Система | Файл | Назначение |
|---------|------|------------|
| CMake | `CMakeLists.txt` | Основная конфигурация, наиболее функциональная |
| Meson | `meson.build` | Альтернатива CMake, популярна в Linux/GNOME |
| Make | `Makefile` | Минималистичный вариант, определение платформы через `uname` |
| pkg-config | `zaster.pc.in` | Механизм обнаружения, используется совместно с Make/Meson |

Все системы реализуют единую логику:
1. Определение платформы (таргета)
2. Подключение prebuilt-библиотек из `prebuilt/<target>/`
3. Fallback на сборку из исходников (где возможно)

**Важно:** `Makefile` в корне (конфигурация для потребителей) и `Makefile` в `lib/`/`cli/` (сборка исходников) имеют кардинально разное назначение.

### Опция ZASTER_LINK_ZSTD

CMake-опция `ZASTER_LINK_ZSTD` (по умолчанию `ON`) управляет линковкой libzstd:
- `ON` — линкуем `prebuilt/<target>/libzstd.a` (или собираем из исходников)
- `OFF` — пользователь сам линкует свою версию libzstd; заголовки zstd всё равно используются наши

Аналогичная механика реализуется в сборочных конфигурациях других языков (build tags в Go и т.д.).

## Go

Файлы `go.mod` и `zaster.go` в корне репозитория.

Go-модули требуют, чтобы все файлы, на которые ссылается CGo, находились внутри модуля. CGo не может ссылаться на файлы из родительской директории — поэтому Go живёт в корне.

CGo не вызывает Makefile — компилирует `.c` файлы напрямую через директивы `#cgo`.

## Rust

Директория `rust/` — `Cargo.toml`, `build.rs`, `src/lib.rs`.

`build.rs` свободно ссылается на `../prebuilt/` и `../zaster.h` — у Rust нет ограничений Go.

## C#

Директория `csharp/` — `.csproj`, P/Invoke обёртки.

Использует динамические библиотеки (`.dll`/`.so`/`.dylib`), которые генерируются из статических.

## Python

Директория `python/` — `pyproject.toml`, cffi/ctypes.

Распространяется через PyPI как platform-specific wheels с упакованными динамическими библиотеками.

## Node.js

Директория `nodejs/` — `package.json`, N-API native addon.

Распространяется через npm с prebuilt-бинарниками.
