# Проект Zaster

## Что это

Zaster — монорепозиторий с открытым исходным кодом, высокопроизводительный биндинг над zstd и tar.zst для множества языков программирования.

Предоставляет:

1. **Исходники zstd** последней стабильной версии (вендорятся скриптом `zstd/update.ps1`)
2. **C-библиотеку `libzaster`** — надстройка над zstd с дополнительными возможностями (упаковка/распаковка tar.zst, управление памятью и др.)
3. **Публичный API** для C/C++ (`zaster.h`, `zaster.hpp`) и других языков (Go, Rust, C#, Node.js, Python)
4. **Вспомогательные файлы сборки** (`CMakeLists.txt` и аналоги) для удобного подключения prebuilt-библиотек или сборки из исходников
5. **CLI-утилиту `zaster`** — демонстрация возможностей библиотеки, упаковка/распаковка tar.zst файлов
6. **Готовые статические библиотеки** для всех целевых таргетов (в `prebuilt/`)

## Зачем

Существующие биндинги zstd не дают достаточного контроля над настройками компилятора, кросскомпиляцией и оптимизацией под конкретные архитектуры. Zaster решает это системно — один раз и для всех языков.

Ключевые сценарии:
- Высоконагруженный Rust-сервер: критичен менеджмент памяти и тюнинг под архитектуру
- Go-проект: максимально быстрая распаковка tar.zst файлов

## Структура репозитория

```
/                   — публичный API и конфигурации сборки
├── zaster.h        — публичный C API
├── zaster.hpp      — публичный C++ API (namespace zstd::, namespace zaster::)
├── CMakeLists.txt  — CMake конфигурация для потребителей
├── Makefile        — Make конфигурация для потребителей (альтернатива CMake)
├── meson.build     — Meson конфигурация для потребителей (альтернатива CMake)
├── zaster.pc.in    — pkg-config шаблон
├── go.mod          — Go модуль (CGo биндинг)
├── zaster.go       — Go биндинг
├── zstd/           — исходники zstd (вендорятся через update.ps1)
├── lib/            — исходники libzaster
├── cli/            — исходники CLI-утилиты zaster
├── prebuilt/       — собранные статические библиотеки для всех таргетов
├── dist/           — временная директория для релизных артефактов (в .gitignore)
├── tests/          — тесты (все языки и платформы)
├── rust/           — Rust биндинг (Cargo.toml, build.rs, src/lib.rs)
├── csharp/         — C# биндинг (.csproj, P/Invoke)
├── python/         — Python биндинг (pyproject.toml, cffi/ctypes)
└── nodejs/         — Node.js биндинг (package.json, N-API или ffi)
```

### Почему Go в корне

Go-модули требуют, чтобы все файлы, на которые ссылается CGo, находились внутри модуля или его подкаталогов. CGo не может ссылаться на файлы из родительской директории (`../../zaster.h`). Поэтому `go.mod` и `.go` файлы размещаются в корне рядом с `zaster.h`.

### Почему остальные биндинги в подкаталогах

Rust (`build.rs`), C# (`.csproj`), Python (`pyproject.toml`) и Node.js (`binding.gyp`/`package.json`) — все умеют ссылаться на файлы в родительской директории. Размещение в подкаталогах не создаёт технических ограничений и сохраняет порядок в корне.

### Системы сборки для C/C++

Четыре альтернативных способа подключения для потребителей:

1. **CMake** — основной, наиболее функциональный (уже реализован)
2. **Meson** — популярен в Linux/GNOME-экосистеме
3. **Makefile** — для минималистичных проектов и embedded
4. **pkg-config** — стандартный механизм обнаружения библиотек в Unix

Все четыре реализуют одинаковую логику: определение платформы → подключение prebuilt-библиотек → fallback на сборку из исходников (где возможно).

## Кросскомпиляция

Кросскомпиляция выполняется внутри Docker-образа `ghcr.io/powertech-center/alpine/cross-clang` — там уже есть компилятор Clang, все необходимые тулчейны и утилиты.

## Статические библиотеки

В `prebuilt/` хранятся две статические библиотеки для каждого таргета:
- `libzstd.a` — собранная из вендорных исходников, меняется редко (только при обновлении zstd)
- `libzaster.a` — наша библиотека

Готовые библиотеки нужны потому что:
- На целевой машине может не быть нужной инфраструктуры
- Пользователь может использовать неоптимальные настройки компилятора
- Сборка из исходников — долгий процесс

При наличии готовой библиотеки для таргета — линкуем её. Иначе — собираем из исходников.

10 prebuilt-таргетов покрывают ~99.9% реальных сценариев использования. Fallback на сборку из исходников нужен для экзотических случаев: 32-битные процессоры, мобильные платформы и т.п. Python и Node.js биндинги для таких платформ не предоставляются, но для C/C++, Go и Rust fallback должен оставаться рабочим.

## Текущее состояние и план

### Готово

- **Исходники zstd** — вендорятся, версия 1.5.7
- **libzaster** — модули memory, tar (fs — заглушка)
- **Prebuilt** — `libzstd.a` и `libzaster.a` для всех 10 таргетов
- **C API** — `zaster.h` (агрегатор)
- **C++ API** — `zaster.hpp` (namespace zstd::, namespace zaster::)
- **CMake** — конфигурация для потребителей, определение платформы, prebuilt + fallback
- **CLI** — утилита `zaster`, собранные бинарники в `dist/`
- **Тесты** — базовые CMake-тесты (C, C++, no-zstd)

### Предстоит реализовать

- **libzaster: fs модуль** — файловые утилиты
- **libzaster: многопоточность** — параллельная работа с tar-записями
- **Meson** — `meson.build` для потребителей
- **Makefile** — `Makefile` в корне для потребителей (не путать с `lib/Makefile`)
- **pkg-config** — `zaster.pc.in`
- **Go биндинг** — `go.mod`, `zaster.go` в корне
- **Rust биндинг** — `rust/`
- **C# биндинг** — `csharp/`
- **Python биндинг** — `python/`
- **Node.js биндинг** — `nodejs/`
- **Динамические библиотеки** — `.so`/`.dll`/`.dylib` для C#, Python, Node.js (генерируются из статических `.a`)
- **Тесты** — расширение на все языки и платформы

## Языковая политика

- Весь проект (исходники, комментарии, документация, строковые константы) — **английский язык**
- Директория `.kiro/` — **русский язык** (для внутреннего использования)
- Общение с разработчиком — **русский язык**
